# 08: UE3 mechanisms we plan to rely on

All of this comes from stock UE3/UDK knowledge and is **unverified against ME LE**. Check each item
in Legendary Explorer (script classes, AnimTrees, GFx packages) or Ghidra (native code) and record
the result here.

| # | Hypothesis | Why it matters | How to verify | Result |
|---|-----------|----------------|---------------|--------|
| H1 | The view is built in native `ULocalPlayer::CalcSceneView`, after script `PlayerController.GetPlayerViewPoint` and `Camera.UpdateCamera` | Single hook point for HMD pose plus per-eye projection | Ghidra: find CalcSceneView (via the vtable/RTTI of LocalPlayer). LEX: ME camera classes (`BioCamera`/`SFXCamera`?) | **Partly confirmed (code reading, [09](09-me3tweaks-code-survey.md)).** ConsoleExtension hooks `CalcSceneView` on **LE3** and rewrites FSceneView view/projection matrices (LE3 offsets ViewMatrix 0x90, ProjectionMatrix 0xD0). It also overrides `CameraCache.POV` in `Engine.Camera.UpdateCamera` on all games. **LE1 address found via prior art ([13](13-existing-me-vr-mods.md)):** `CalcSceneView` = `0x4C5300`, called from `FViewportClient::Draw` (`0x4C71A0`) at return address `0x4C7A4E`. **Verified statically** as function starts in `.pdata` (`tools/verify_rvas.py`). FSceneView offsets match LE3 (View `0x90`, Projection `0xD0`). Still needed: an in-process check |
| H2 | UE3's **split-screen** path renders several views per frame, each `ULocalPlayer` with its own `FSceneViewState` (occlusion and temporal history) | Synchronized stereo with isolated per-eye state, the problem Overlord solved by hand | Ghidra: split-screen code in GameViewportClient / scene renderer; check whether ME stripped it | **Refuted by prior art ([13](13-existing-me-vr-mods.md)), [verify].** Halcyon found that UE3-LE runs deferred lighting, bloom, light shafts and DoF for the *first* view of a multi-view family only, so a second view gets a flat right eye and black conversation characters. | H14 | LE1 in-game frame rate can be uncapped above 60 fps | The headset needs 72–90 Hz | Check VSync, then `bSmoothFrameRate`/`MaxSmoothedFrameRate` in the engine ini | **Open.** M0 measured about 190 fps at the menu but a 60 fps lock in game. In VR (M3, 2026-10-07) the heartbeat showed about 89.6 fps (paced by `xrWaitFrame` at 90 Hz) in light scenes, but **51–80 fps** in a heavier one: an irregular cadence against 90 Hz. Halcyon paces presents to a whole number of display periods instead ([13](13-existing-me-vr-mods.md)). **Likely answer (prior art, [verify]):** the cap is `BIOEngine.ini` `SmoothFrameRate` / `MaxSmoothedFrameRate=60`. The game re-syncs the file, so Halcyon rewrites it to `TRUE`/`120` at every attach, keeping the smoothing because cutscene cameras judder without it. **Our install (2026-10-07):** `BIOEngine.ini` has `SmoothFrameRate=FALSE` (cap off, which is why VR reached 89.6 fps), `MaxSmoothedFrameRate=60`, and `DesiredRange=DynamicRange_Auto` (HDR on, hence the FP16 backbuffer). `GamerSettings.ini` has `UseVSync=True`, so Present also waits on the *desktop monitor's* vblank: a second clock beating against `xrWaitFrame`. Turn VSync and HDR off for VR |
| H17 | Any script native can be called from C++ through `UObject::ProcessEvent` with the SDK's parms struct | Bone queries, reflection fix, hiding bones | Decrypted code: LE1 ProcessEvent `0x12DD20`, the natives | **Partly refuted (code, 2026-10-08).** Natives read their parameters from their own `EX_NativeParm` (0x29) bytecode. The handler (`0x11F210`) binds an out parameter to the caller's parms only for a non-null result buffer, and `P_GET_TARRAY_REF` steps with a null one. So **natives with an `out array<>` parameter (e.g. `GetBoneNames`) return nothing**. Return values (written straight to `Parms + ReturnValueOffset`) and plain inputs work. In-process confirmation logged by the skeleton probe [verify] ([14](14-vrik.md)) |
